# ChangeGuard 产品说明

## 1. 产品定义

ChangeGuard 是给小型软件企业使用的生产变更风险门禁。它在现有 Git 与 CI/CD 流程之间增加一层轻量控制：统一接收 SQL、应用配置和 Kubernetes 清单，运行确定性检查，组织人工审批，并用一次性变更通行证确保流水线部署的是已审批制品。

一句话价值主张：

> 用较低接入成本，降低“高风险变更漏审”和“审批内容与实际部署内容不一致”的概率，同时留下可审计证据。

企业购买的不是“多一个扫描器”，而是一份低成本发布保险：一次误发布造成的停机、回滚和客户解释成本，以及每周重复人工审核与审计取证的人力成本，都可能高于工具订阅费。ChangeGuard 不承诺虚构的固定 ROI，而是让客户用未授权发布次数、单次审核时长、重复风险命中率和证据准备时长衡量价值。

## 2. 目标客户

优先服务以下团队：

- 30～300 人的软件、SaaS、电商、企业服务或数字化团队；
- 有 5～100 个独立服务，已经使用 Git 与 Jenkins、GitLab CI、GitHub Actions 等流水线；
- 生产变更依赖群聊、表格或通用工单，审核标准不统一；
- 没有预算和人员实施大型 ITSM、数据库审计或发布治理套件；
- 开始面对客户安全问卷、等保、ISO 27001、SOC 2 或内部审计要求。

典型购买者是 CTO、研发负责人、DevOps 负责人或安全负责人。日常使用者是开发者、发布审核人和技术负责人。

## 3. 企业痛点与购买动机

### 3.1 审批与部署脱节

常见流程只批准工单文字或截图，流水线并未校验最终文件。开发者在审批后修改脚本、替换镜像或调整配置，审核结论便失去意义。

ChangeGuard 对审批制品计算摘要，通行证绑定变更单、环境、制品摘要、有效期和使用次数。CI 在部署前消费，任何不一致都阻断。

### 3.2 人工审核成本高且标准不一致

审核人需要反复检查危险 SQL、明文密钥、特权容器、latest 镜像等重复问题。高峰期容易漏看，也很难解释为什么通过。

ChangeGuard 先运行确定性规则并给出规则编号、证据位置、风险级别和整改建议。审核人把时间留给业务影响和发布窗口等需要人判断的内容。

### 3.3 事故后缺少完整证据

群聊里的“可以上”无法稳定回答谁提交、检查了什么、谁批准、流水线最终部署了什么，以及通行证是否被重复使用。

ChangeGuard 把变更、发现项、整改、审批和通行证事件串成可查询的审计记录，降低复盘与外部审计取证成本。

### 3.4 大型治理产品太重

小企业通常不愿为复杂流程平台投入专职管理员，也不希望替换已有 Git 和流水线。

ChangeGuard 只守住生产部署前的关键节点，使用 HTTP API 接入现有 CI；部署、规则和角色模型保持小而明确。

## 4. 用户旅程

### 4.1 开发者

1. 选择应用和目标环境，创建变更单。
2. 上传或粘贴 SQL、配置或 Kubernetes 制品。
3. 查看规则发现项，修复制品并重新检查。
4. 补充变更目的、回滚方案和发布窗口，提交审批。
5. 审批通过后，由实际审批人在变更详情签发一次性通行证，并立即保存到 CI secret；明文 Token 不会再次显示。
6. 流水线在部署前消费通行证；结果回写审计记录。

### 4.2 发布审核人

1. 查看制品差异、摘要和阻断项。
2. 核对回滚与业务影响证据。
3. 对发现项要求整改，或在权限范围内批准/拒绝。
4. 必要时吊销尚未消费的通行证。
5. 通过审计记录确认实际部署制品与批准制品一致。

### 4.3 技术负责人

1. 纳管服务，分配提交与审核权限。
2. 管理组织级规则和应用级例外。
3. 查看阻断率、重复问题和审计导出。
4. 根据事故复盘补充确定性规则。

## 5. v1 功能需求

### 5.1 变更工作台

- 创建、编辑、提交、批准和拒绝变更单；生产治理闭环只能由 CI 成功消费通行证后自动完成；
- 关联组织、应用、环境、提交人和审核人；
- 展示制品摘要、检查批次、发现项、评论与审计事件；
- 禁止提交人自审，限制跨应用和跨组织访问。

### 5.2 三类确定性门禁

- SQL：检查高风险 DDL/DML、缺少条件、回滚与执行约束；生产签证还要求在隔离 PostgreSQL 影子事务中实际执行 SQL 与回滚脚本；
- 配置：检查疑似明文敏感信息、不安全开关与过宽访问设置；
- Kubernetes：检查镜像标签、权限、主机挂载、资源与健康检查；
- 每个结果必须包含稳定规则编号、严重级别、命中位置和解释；
- 同一制品与同一规则版本应得到相同结果。

### 5.3 变更通行证

- 仅对满足规则和审批条件的变更签发；
- 绑定组织、变更单、目标环境和制品 SHA-256，并通过不可变的变更记录关联应用；
- 短时有效，默认一次消费，数据库只保存令牌摘要；
- 过期、吊销、重复消费、环境或摘要不匹配必须失败；
- 签发、查看状态、吊销、消费均产生审计事件；
- 原始令牌只在签发时返回一次，日志和页面不得再次显示。

### 5.4 审计与运营

- 支持按变更单查询完整时间线；
- 支持导出不含敏感原文的审计报告；
- 健康检查与指标不得泄露凭据；
- 重要失败应提供可操作错误原因，而不是统一返回“系统错误”。

## 6. 商业化建议

建议按照“纳管服务数”订阅，用户数在合理范围内不计费。原因：

- 服务数与风险覆盖面积、规则执行量和审计价值更相关；
- 开发、审核和运维都应参与，按席位收费会抑制协作；
- 客户扩展微服务时自然升级，收入与使用规模一致；
- 销售和预算口径简单，容易从单团队试点扩展到全公司。

可采用以下产品阶梯，价格需结合市场验证后确定：

| 版本 | 建议范围 | 主要目的 |
| --- | --- | --- |
| Community | 5 个服务以内，自托管 | 个人作品展示、小团队试用和获客 |
| Team | 20 或 50 个服务 | 三类门禁、审批、通行证、基础审计 |
| Business | 100 个及以上 | SSO、更长审计保留、组织策略、备份恢复与支持服务 |
| Enterprise | 定制 | 私有化交付、合规协助、SLA 和专属支持 |

可选增值项包括规则包、合规报表、企业身份集成和部署支持；不建议把基础安全修复或关键审计能力拆成额外收费项。

客户愿意续费的核心指标不是“扫描了多少次”，而是：

- 生产部署被未审批制品绕过的次数是否降为零；
- 审核人处理单个变更的中位时间是否下降；
- 重复高风险问题是否持续减少；
- 审计取证是否能从数天缩短到数分钟。

## 7. 非目标

v1 不承担以下职责：

- Git 托管、构建、发布编排或集群操作；
- 生产 SQL 执行、影子压测、P99/锁等待预测；
- 使用 AI 或概率评分自动决定生产放行；
- 完整 ITSM、CMDB、GRC、SIEM 或可观测平台；
- 代码质量、API 兼容性、业务回归或供应链全量扫描；
- 保存真实生产密钥或把变更制品当作密钥仓库。

## 8. 成功标准

项目达到“小企业可试点”的最低标准时，应满足：

- 三类制品都有可重复的正反例测试；
- 关键状态迁移和权限边界有自动化测试；
- 通行证的签发、消费、过期、吊销和重放防护有集成测试；
- Jenkins 或 GitLab CI 至少完成一次真实阻断演示；
- 界面可在桌面端完成创建、检查、审批和查看审计的主流程；
- 文档明确区分静态证据、人工判断和真实运行结果；
- 新环境可按 README 在可接受时间内启动并复现演示。

## 9. 面试叙事

推荐用四段讲清项目：

1. **问题**：小企业的生产变更散落在 SQL、配置和 Kubernetes 文件里，审批与最终部署没有强绑定。
2. **选择**：没有做大而全的发布平台，而是在 CI 部署前增加确定性规则、人工审批和一次性通行证。
3. **难点**：状态机与权限、制品摘要绑定、令牌只存哈希、并发消费防重放、审计一致性和可信测试。
4. **价值**：减少审核重复劳动，阻止审批后替换制品，并提供低成本审计证据；商业上按纳管服务数订阅。

面试时应明确区分“已实现且有测试”“已实现但未完成环境验证”和“后续规划”。不要用随机模拟数据包装性能能力，也不要把静态扫描描述为生产验证。
