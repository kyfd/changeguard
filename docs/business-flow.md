# ChangeGuard 业务流程

## 1. 核心业务

ChangeGuard 管理的不是单一数据库脚本，而是一次生产发布中最容易绕过代码评审的三类制品：

- SQL 迁移；
- 应用配置；
- Kubernetes 清单。

三类制品进入同一张变更单、同一次审核和同一个 CI 门禁。企业购买的核心价值是：**让审批对象与实际部署对象保持一致，并留下可审计证据。**

## 2. 角色

| 角色 | 主要权限 |
| --- | --- |
| 后端开发 | 创建、编辑、提交、整改自己有权限的应用变更 |
| 发布审核人 | 查看授权应用的证据，要求整改，批准或拒绝 |
| 技术负责人 | 管理企业、成员、应用、规则和审核授权 |
| CI/CD | 只能使用一次性通行证校验并消费指定变更，不能代替人工审批 |

提交人与审核人必须分离。企业管理员身份不应自动绕过应用级数据边界。

## 3. 主流程

~~~mermaid
sequenceDiagram
    participant D as 开发者
    participant C as ChangeGuard
    participant R as 审核人
    participant P as CI/CD
    participant T as 部署目标

    D->>C: 创建变更单并提交一种或多种受支持制品
    C->>C: 对原始字节计算 SHA-256，保存可审阅的脱敏表示
    C->>C: 运行确定性规则
    alt 存在阻断项
        C-->>D: 返回规则编号、位置与整改建议
        D->>C: 更新制品并重新检查
    else 无阻断项
        C-->>R: 进入待审批
        R->>C: 批准或拒绝
        alt 审批通过
            R->>C: 由实际审批人签发短时通行证
            C-->>R: 明文 Token 仅本次响应显示
            P->>P: 从实际发布文件重算聚合 SHA-256
            P->>C: 消费通行证并提交摘要
            alt 完全匹配且未过期
                C-->>P: 通行证标记已用，治理闸门闭环
                P->>T: 执行既有部署脚本
            else 任一条件不匹配
                C-->>P: 拒绝；HTTP 访问日志保留最小失败元数据
            end
        else 审批拒绝
            C-->>D: 返回审核意见
        end
    end
~~~

## 4. 创建变更

开发者至少需要填写：

- 应用、目标环境和计划时间；
- 仓库、分支、Commit 等来源信息；
- 一个或多个 DATABASE、CONFIG、KUBERNETES 制品；
- 业务目的、影响范围、发布策略和回滚方案。

服务端为每个制品计算摘要，并计算整张变更单的聚合摘要。制品正文不得被当作秘密存储；疑似敏感字段应在保存前拒绝、脱敏或只保留安全证据。

## 5. 检查与整改

每次提交或更新制品都创建新的检查批次，检查结果必须关联：

- 变更单版本；
- 规则集版本；
- 制品类型与摘要；
- 规则编号和严重级别；
- 命中位置与可解释证据；
- 检查时间和检查器版本。

阻断项未解决时不能进入审批。非阻断项可以进入人工判断，但必须在审批界面可见。

“未命中规则”表示当前规则集没有发现已知模式，不得写成“生产验证通过”。配置和 Kubernetes 制品也不能用固定 PASSED 结果代替真实规则。

## 6. 审批

审核人关注三类信息：

1. 自动检查是否仍有阻断项；
2. 业务影响、发布窗口、观察指标和回滚方案是否合理；
3. 当前看到的制品摘要是否是开发者最后一次提交的版本。

以下情况必须使已有审批失效并回到检查或待审批：

- 任一制品内容、制品集合或参与摘要的制品元数据变化；
- 应用、目标环境、Commit 或发布策略变化；
- 规则集升级后新增阻断项；
- 审核权限被撤销或成员被停用。

## 7. 变更通行证

批准不应直接等于“任何流水线都可发布”。只有完成本次审批的实际审核人可以为已批准变更签发通行证：

- 绑定企业、变更单、环境、规则版本、实际审批人和制品摘要，并通过变更记录关联应用；
- 默认 10 分钟有效，可在 1～30 分钟范围内配置；
- 默认只允许成功消费一次；
- 原始令牌只展示一次；
- 支持发布取消时吊销。

CI 消费成功后才执行生产部署。消费失败必须停止，不允许把 ChangeGuard 异常当作自动放行理由。

目标接口见 [CI/CD 接入指南](ci-integration.md)。

## 8. 异常流程

| 场景 | 系统行为 |
| --- | --- |
| 阻断规则命中 | 保持 CHECK_FAILED，要求更新制品 |
| 审核拒绝 | 记录意见，进入 REJECTED 或退回草稿 |
| 审批后修改制品 | 撤销审批与未消费通行证，重新检查 |
| 通行证过期或吊销 | CI 返回失败，不执行部署 |
| 摘要或环境不匹配 | 返回 403，流水线阻断；服务访问日志不得包含 Token |
| 并发消费 | 只有一个请求成功，其他请求返回冲突 |
| Gate 服务不可用 | 流水线失败关闭，人工处理 |
| 部署脚本失败 | ChangeGuard 不将其误写为“门禁失败”；发布系统回传流水线终态，运维系统另行回传事故或回滚执行证据 |

## 9. 审计时间线

至少记录：

- 创建、编辑、提交和重新检查；
- 规则版本与发现项变化；
- 整改、评论、批准和拒绝；
- 通行证签发、成功消费、过期状态落盘和吊销；
- CI 消费通行证后形成的治理闭环；
- GitLab/Jenkins 发布终态、事故关联、回滚执行终态和业务 SLI 前后对比；
- 企业、成员、应用和规则配置变更。

审计事件写入应与对应业务状态保持一致。报告只能陈述系统实际记录的事实，不能用模板生成“已恢复”“性能稳定”等未验证结论。

## 10. 面向企业的结果指标

产品看板应优先展示：

- 未审批或摘要不一致部署被阻断的次数；
- 变更从提交到审批的中位耗时；
- 各规则的重复命中率和整改时间；
- 通行证过期、吊销和重放尝试；
- 按应用统计的变更量、阻断率和审计完整度。
- 有样本约束的发布失败率、发布后需要事故处置或回滚的比例；
- 事故解决时长、回滚成功率，以及显式业务目标达成率。

没有外部样本时必须标记不可观测；模拟耗时、固定通过率、审批通过率和随机性能数据不得替代真实发布结果、事故或业务 SLI。
