# ChangeGuard 4.0：破坏性清理与部署一致性

状态：**4.0.0 已合并到 main，随 `v4.0.0` 标签发布**。发布包由 Release 工作流产出；生产主机部署仍待执行（见文末未验证项）。

## 目标

3.1 把配置、升级和单实例边界留在"文档提醒 + 兼容层"上，4.0 把它们改成代码里的硬约束：

1. 环境变量只接受 `CHANGEGUARD_*`，遗留 `DBGUARD_*` 一律失败关闭（不再是"仍可读 + 告警"）。
2. 文件状态后端与 Agent 存储的单实例语义变成启动期强制，而不是只写在文档里。
3. 发布包必须声明自己携带的组件（core + agent），预检拒绝"只有核心"的隐式半包。

## 已实现（本分支）

### B1 单一环境变量前缀

- `internal/runtimeconfig/brand.go`：删除 `CHANGEGUARD_* → DBGUARD_*` 别名层，改为 `rejectLegacyBrandEnvironment()`——进程环境里出现任何 `DBGUARD_*` 键即失败关闭，错误信息只列键名（不含值）并给出迁移命令。
- `internal/runtimeconfig/environment.go`：环境文件内出现旧前缀键同样失败关闭，并报告行号；移除 `Summary.LegacyKeys`；生产 profile 的提示文案不再提"旧键仍被接受"。
- 其余 Go 包（`store`、`auth`、`httpapi`、`agent`、`integration`、`modelprobe`、`experiment` 等）统一读取 `CHANGEGUARD_*`。
- 部署资产与活文档改名：`.env.example`、`compose.e2e.yml`、`.github/workflows/ci.yml`、`deploy/production/*`、`deploy/upgrade/*`、README 与 docs（历史记录类文档保留当时的事实）。
- 迁移工具 `deploy/production/changeguard-migrate-env.sh`：只改键名不动值，写入前备份（`<file>.pre-4.0`，绝不覆盖已有备份），同名 canonical/legacy 值冲突时失败关闭，`--dry-run` 支持。

### B2 单实例守卫

- Go：`internal/store/instance_lock*.go`。文件状态后端在触碰状态文件之前取得 `<state>.instance.lock` 独占锁（Unix `flock`，Windows `CreateFile` + `dwShareMode=0`，其它平台失败关闭）；第二个进程返回 `ErrInstanceLocked` 并指向 `postgres` 后端。PostgreSQL 后端保持多实例语义。
- Agent：`agent-app/app/instance_lock.py` 在 FastAPI lifespan 中取得 `<task-store>.instance.lock`；拿不到锁直接启动失败。`--workers > 1` 与多副本部署因此不可能静默共享 JSON/SQLite 存储。

### B3 发布包组件清单（校验端）

- `deploy/lib/release_manifest.py`：组件清单的权威校验（schema `changeguard-release/v3` 必含 `core`，除非显式 `--core-only` 否则必须含 `agent`；组件名唯一、路径无穿越、摘要 64 位十六进制）。v2 包只在显式 `--core-only` 下接受。
- `deploy/upgrade/changeguard-upgrade-preflight.sh`：schema 与组件判定改为导入上述模块；模块缺失即 `manifest_library_missing` 失败关闭；输出 `components=` 汇总供调用方核对。
- `deploy/production/changeguard-agent.service`：Agent 的 systemd 单元（只监听 loopback、独立数据目录、强制实例锁）。

## 本阶段未完成（需要能跑 Linux root 的环境）

以下工作会改变升级与安装的语义，必须由 CI 的隔离安装/回滚回归（`tests/deploy/test_upgrade.py`，要求 Linux + root）验证后才能合并：

1. （已完成，见下方"生产端已完成"一节）发布工作流把 manifest 升到 `changeguard-release/v3` 并把 `agent-app/` 打进包。
2. 安装器把 Agent 组件安装到版本目录（准备 venv、安装 `changeguard-agent.service`）。
3. 升级器/回滚：切换 `current` 软链后同时重启核心与 Agent，任一失败回滚两个组件。
4. 预检对"目标机正在运行的 Agent 版本"与包内 agent 组件摘要逐项核对（当前只核对版本配套性）。

本机（Windows + WSL，非 root）无法执行该回归，因此这些改动一律未提交，避免把无法验证的破坏性脚本改动放进分支。

## 迁移路径（3.1.9 → 4.0.0）

1. 停核心与 Agent，备份 Go 数据、迁移见证、配置/密钥、Agent 任务 JSON、检查点 SQLite、知识与评测 JSON。
2. `sudo deploy/production/changeguard-migrate-env.sh --file /etc/changeguard/core.env --dry-run` 查看将改名的键；去掉 `--dry-run` 执行迁移（会生成 `.pre-4.0` 备份）。
3. 同步更新 systemd 单元与环境模板（`changeguard.service`、watcher 单元改名后的键）。
4. 升级前确认 `--core-only` 是否真的适用：4.0 的完整包同时携带核心与 Agent，只声明 core-only 意味着放弃 Agent 组件核对。
5. 回滚：恢复旧版本软链与 `.pre-4.0` 环境文件；4.0 的锁文件（`*.instance.lock`）不含状态，可直接删除。

## 生产端已完成（第二阶段，Linux root 实测）

上面"本阶段未完成"的四项现已实现，并在 WSL2 ext4（root、真实 POSIX 权限）上通过了原有隔离安装/回滚回归：

1. `deploy/production/build-core-git-release.sh` 从提交导出 `agent-app/`，manifest 升为 `changeguard-release/v3` 并声明 `components`（core=二进制摘要，agent=`release_manifest.tree_digest` 树摘要），SHA256SUMS 覆盖整个组件树。
2. `.github/workflows/release.yml` 打包时一并放入 `agent-app/`。
3. `deploy/production/changeguard-core-install.sh` 接受 v3 清单、核对 core 组件摘要，并在安装后重算 Agent 树摘要逐字节比对；不一致则**删除刚落地的版本目录**再失败关闭（不留下"看起来装好了"的目录）。
4. `changeguard-upgrade.sh` / `changeguard-upgrade-watcher.sh`：包内带 Agent 组件且系统装有该 unit 时（`CHANGEGUARD_AGENT_SERVICE` / `CHANGEGUARD_AGENT_UNIT_DIR`，watcher 可用 `CHANGEGUARD_MANAGE_AGENT=off` 关闭），核心与 Agent 在同一次切换里重启，任一失败回滚两者。

验证：`sudo python3 -B -m unittest discover -s tests/deploy -v` → **57 项全部通过，无 skip**，其中新增 4 项覆盖两组件一起重启、Agent 重启失败时两者一起回滚、组件摘要不符被拒并清理目录、旧格式包必须显式 `--core-only`。

4.0.2 补上 watcher 的缺口：重启 Agent 后必须探活通过才记成功，探活失败与核心一起回滚。仍未验证：真实生产主机部署、真实 systemd 服务重启。真实发布包已由 v4.0.0 / v4.0.1 的 Release 工作流产出。
