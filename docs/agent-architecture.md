# 变更准备 Agent 架构说明

本文回答一个问题：**为什么模型不控制审批和发布。**

## 1. 职责边界

```
人：提需求、确认材料、审批、决定发布
      │
      ▼
Agent 服务（Python）        识别缺失信息、检索规范、生成草案、调用确定性检查
      │  只读工具
      ▼
治理后端（Go）              身份、权限、状态机、通行证、发布门禁
```

| 能力 | 谁拥有 | 为什么 |
| --- | --- | --- |
| 生成草案 | Agent | 这是模型擅长的部分 |
| 判定风险等级、阻断项 | **确定性扫描** | 同样输入必须得到同样结论 |
| 决定能否继续 | **人** | 审批是责任行为，不能外包给概率系统 |
| 签发通行证、放行部署 | **治理后端** | 需要组织隔离、职责分离与原子消费 |

## 2. 三条结构性理由

### 2.1 模型的输出是概率性的，门禁必须是确定性的

`scan_sql` 是纯函数：相同 SQL、相同表结构快照必然得到相同结论，可复现、可回归。
模型不同：同一个提示可能给出不同草案。

如果让模型决定"能不能过"，门禁就变成了抽奖。所以设计上：

- 检查结果字段 `deterministic_check` 只由扫描写入，模型无权修改；
- 模型的风险判断放在 `ai_advice`，**明确标注不参与放行**；
- 扫描工具失败时状态是 `FAILED` → 任务 `CHECK_BLOCKED`，**不是"通过"**。

### 2.2 审批是责任，不是能力

审批意味着"我确认这份材料可以上生产"。把这件事交给模型，出现事故时无法追责，
也无法解释"为什么系统认为它是安全的"。

因此首版保留**材料确认**（确认 AI 理解的需求和生成内容是否正确）与
**正式审批**（由有权限且满足职责分离的人决定）两个独立概念，并且只把后者交给治理后端。

### 2.3 写路径会放大一切错误

只读时，注入的最坏后果是"一条错误建议"；一旦能写，后果变成"一个看起来像常规变更的恶意变更"。

所以首版边界是：**Agent 可见的工具全部只读**，写操作由确定性编排在已认证业务接口上执行。
这正是 `docs/adr/0002-...` 被标注为**延后提案**的原因——它描述的是第二阶段，不是首版。

## 3. 失败语义（最容易被做错的地方）

| 情况 | 错误做法 | 本设计 |
| --- | --- | --- |
| 检索不到规范 | 让模型"凭经验写" | 返回 `ok=False`，草案标注依据不足 |
| 扫描工具超时 | 视为"无问题" | `check.status=FAILED` → `CHECK_BLOCKED` |
| 模型返回非法 JSON | 静默截断/猜测 | 有限重试后 `FAILED`，错误信息明确指出原因 |
| 模型引用不存在的证据 | 接受引用 | 直接拒绝（`引用了不存在的证据 ID`） |
| 后端返回 403 | 降级为"用缓存数据" | 工具显式失败，不重试 |
| 输入含注入 | 继续生成 | `INPUT_REJECTED`，停止处理 |

统一的判断标准：**失败必须比成功更难被误认为成功。**

## 4. 有限循环与预算

Agent 的不确定性主要来自"什么时候停"。本设计用三个硬约束替代"看起来差不多了"：

1. `max_revisions` 是硬上限，达到即停；
2. 检查结论与上一轮完全相同视为**无进展**，提前停止，避免空转消耗；
3. 工具超时、任务超时都有显式上限，超时按失败处理，不让状态停在 `RUNNING`。

## 5. 可回滚与可解释

- 任务事件（`events`）记录每一步做了什么、结论是什么，**不记录思维链**；
- 任务的失败、阻断、拒绝都是显式状态，可查询、可复盘；
- 取消会真正停止后续工作，而不是"标记为取消但继续跑"。

## 6. 尚未解决

- **多实例一致性**：任务状态存文件，仅适配单实例。
- **评估覆盖**：当前 11 例，未拆分开发集与保留测试集，且不含真实模型基线。
- **RAG 质量**：关键词基线对中文只做二元组，无关查询可能召回弱相关片段；
  向量检索接口已预留，但尚未做对照实验。
- **第二阶段的写路径**：服务账号、可信发起人归属、创建幂等、自审拦截、失败恢复
  均未实现，属于 `docs/adr/0002` 的范围。
