# 案例 001：订单表并发新增复合索引（成功）

> 合成案例，用于演示"历史案例检索"。应用与环境均为虚构。

| 字段 | 内容 |
| --- | --- |
| 案例编号 | CASE-001 |
| 应用 | `order-service`（订单服务） |
| 环境 | 生产 / PostgreSQL 15 |
| 变更类型 | 数据库变更（新增索引） |
| 结果 | 成功，无故障 |
| 时间窗口 | 2026-07-18 21:30–22:10（北京时间） |

## 背景

订单列表页按 `user_id` 过滤并按 `created_at` 倒序分页，P99 约 2.1 秒。
现有索引只有 `idx_orders_user_id`，无法覆盖排序。

## 执行内容

```sql
SET lock_timeout = '3s';

CREATE INDEX CONCURRENTLY idx_orders_user_created
  ON orders (user_id, created_at DESC);
```

未使用事务块，脚本中不含 `BEGIN` / `COMMIT`。

## 观察数据

| 指标 | 变更前 | 变更后 |
| --- | --- | --- |
| 查询 P99 | 2.1s | 42ms |
| 写入 P99 | 18ms | 19ms |
| 最长锁等待 | — | 210ms |
| 建索引耗时 | — | 6 分 40 秒 |

## 复盘要点

1. 复合索引顺序是"等值列 + 排序列"，与查询形态一致，避免了额外 Sort。
2. `CONCURRENTLY` 使写入几乎无感知，最长锁等待 210ms，远低于 3 秒超时阈值。
3. 该场景下**不需要**回滚，索引保留。
4. 关键经验：**先设置 `lock_timeout`，再执行并发建索引**，避免意外长时间排队。
