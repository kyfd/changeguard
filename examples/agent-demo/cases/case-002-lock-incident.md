# 案例 002：非并发建索引导致写入阻塞（事故）

> 合成案例，用于演示"规范约束从哪来"。应用与环境均为虚构。

| 字段 | 内容 |
| --- | --- |
| 案例编号 | CASE-002 |
| 应用 | `order-service`（订单服务） |
| 环境 | 生产 / PostgreSQL 14 |
| 变更类型 | 数据库变更（新增索引） |
| 结果 | **事故：写入阻塞 8 分 12 秒** |
| 时间 | 2026-03-05 14:20（业务高峰） |

## 发生了什么

变更脚本使用了非并发方式建索引，且没有设置 `lock_timeout`：

```sql
-- 事故脚本（反面示例，不要照抄）
CREATE INDEX idx_orders_user_created ON orders (user_id, created_at DESC);
```

`CREATE INDEX` 需要持有 `ACCESS EXCLUSIVE` 锁。由于当时存在一个持续 4 分钟的长事务，
建索引请求在锁队列中排队，**该队列会阻塞后续所有对该表的访问**，包括普通查询。

## 影响

| 指标 | 数值 |
| --- | --- |
| 写入阻塞时长 | 8 分 12 秒 |
| 受影响订单量 | 约 11.4 万笔下单请求超时 |
| 最长锁等待 | 4 分 31 秒 |
| 恢复方式 | 终止长事务 + 取消建索引 |

## 根因

1. **未使用 `CONCURRENTLY`**：违反热表索引变更规范。
2. **未设置 `lock_timeout`**：请求一直排队而不是快速失败。
3. **窗口选择错误**：在业务高峰执行 DDL。
4. **长事务未排查**：变更前未检查 `pg_stat_activity` 中的长事务。

## 由此产生的规范条款

- 热表必须使用 `CREATE INDEX CONCURRENTLY`（规范 1.1）
- 并发建索引不得放在事务中（规范 1.2）
- 必须设置 `lock_timeout`（规范 2.1）
- 阻塞超过 30 秒视为事故级别（规范 2.2）
- 计划时间必须是明确时刻并避开高峰（规范 4.2）

## 复盘结论

**这条规范不是拍脑袋定的，是这次事故换来的。** 变更准备 Agent 在生成草案时，
若发现热表 + 非并发建索引，应直接判定为阻断项，而不是"建议优化"。
