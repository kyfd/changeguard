# SQL 变更规范（合成示例）

> 本文是**示例规范**，用于演示检索与引用；不代表任何组织的真实制度。
> 文档版本：v1.3　生效日期：2026-06-01　适用范围：PostgreSQL 生产库

## 1. 索引变更

### 1.1 热表必须使用并发建索引

对日均写入超过 10 万行的表，新增索引必须使用 `CREATE INDEX CONCURRENTLY`。
非并发方式会持有 `ACCESS EXCLUSIVE` 级别的表锁，阻塞该表的读写。

### 1.2 并发建索引不能在事务中执行

`CREATE INDEX CONCURRENTLY` 无法在事务块内运行。因此：

- 迁移脚本中不得包含显式 `BEGIN` / `COMMIT`；
- 同一脚本里不得与其他需要事务的 DDL 混排；
- 失败后会残留 `INVALID` 索引，必须显式 `DROP INDEX` 后重试。

### 1.3 索引列顺序

等值条件列在前，范围与排序条件列在后，符合 B-tree 最左前缀原则。
排序列方向应与查询排序一致，避免额外的 Sort 节点。

## 2. 锁与超时

### 2.1 必须设置超时

所有 DDL 变更必须先设置 `lock_timeout`，其次设置 `statement_timeout`。
建议值：`lock_timeout = '3s'`，`statement_timeout = '30min'`（并发建索引较慢时可放宽）。

### 2.2 不得长时间持有排他锁

阻塞超过 30 秒的锁等待视为事故级别，必须中止并改为低影响方案。

## 3. 数据变更

### 3.1 禁止无条件更新或删除

`UPDATE` 与 `DELETE` 必须带 `WHERE`，且必须在变更单中说明影响行数的估算依据。

### 3.2 大表数据回填必须分批

单次影响行数超过 10 万的更新必须拆分为批次，并在批次之间留出间隔。

## 4. 变更材料完整性

### 4.1 必须提供回滚方案

任何变更都必须提供可执行的回滚语句或明确说明"不可回滚"及其理由。

### 4.2 必须提供明确的时间窗口

计划执行时间必须是**带时区**的明确时刻，不接受"周五晚上"这类模糊表述。
默认窗口为北京时间 21:00–24:00，且需避开同应用的上下游发布窗口。

### 4.3 草案必须标注假设

生成的内容必须区分"已确认事实"与"假设待确认项"。缺少表结构证据时不得凭空推断字段名。
